## 1. 需求溯源：你最初说的是什么

### 1.1 原话拆解

| 你的原话                         | 本质问题                         | 一句话验收标准                             |
| -------------------------------- | -------------------------------- | ------------------------------------------ |
| 「某个补剂需要隔一天吃，怕记混」 | 今天到底该不该吃？               | 打开就看到「今天吃 / 今天不吃，下次 X 日」 |
| 「还有停药期」                   | 有一段时间不吃，这段时间别提醒我 | 停用期间该补剂整体静音，且说清什么时候恢复 |

### 1.2 「怕记混」其实包含三个问题

这一点在既有文档里从未被明确拆开过，但它决定了功能边界：

| 编号   | 用户的真实疑问 | 对应能力         | 频次               |
| ------ | -------------- | ---------------- | ------------------ |
| **Q1** | 今天该吃什么？ | 今日清单（四态） | 每天 1–3 次        |
| **Q2** | 我吃了吗？     | 打卡             | 每天 3–7 次        |
| **Q3** | 昨天吃了吗？   | 回看 / 日历      | 偶尔（怀疑记错时） |

**Q1 + Q2 是每天发生的高频动作，Q3 是低频补位。** 现有系统的绝大部分复杂度，都花在既不回答 Q1、也不回答 Q2/Q3 的地方。

### 1.3 需求采集五要素

| 要素 | 内容                                                                                                                  |
| ---- | --------------------------------------------------------------------------------------------------------------------- |
| 背景 | 自用工具。补剂种类多，存在隔天吃、周期性吃、服用一段时间后停用的情形，靠记忆容易混                                    |
| 用户 | 单人（自己）。使用场景以**电脑前**为主（PC 优先，D5）；早餐桌、睡前在手机上的情形**后期再适配**，本期只要求窄屏不破坏 |
| 目标 | 打开 5 秒内知道「今天吃什么」，吃完能打上勾，事后能回看                                                               |
| 范围 | 包含：补剂、计划（含节奏）、记录、停药、回看。不包含：医疗建议、营养计算、社交、云同步、移动端专门适配                |
| 约束 | 纯前端、本地存储、离线可用、不引入后端、**PC 优先且窄屏不破坏**                                                       |

### 2.2 结论

**约 45% 的规范篇幅，服务于「库存与撤销的正确性」这一件事。**

而这件事的根源是一个技术选择：**用软删除实现「撤销」**。为了回答「恢复一条被撤销的记录时，要不要再扣一次库存」，整个 4 态状态机（`deducted` / `not_deducted` / `was_deducted` / `unknown`）、库存流水表、purge 语义、unknown 二选一对话框、双扣警告，全部是为了这一个问题而生。

**如果把「撤销」改成直接删除记录 + 金额/余量直接加回，这整套东西一次性消失。**

## 4. 核心功能定义（L0，可直接开发）

### 4.1 整个产品只有三个概念

| 概念     | 回答的问题         | 说明                                                     |
| -------- | ------------------ | -------------------------------------------------------- |
| **补剂** | 我有哪些？         | 一个名字 + 每次吃多少 + 单位；余量可选                   |
| **计划** | 我该什么时候吃？   | **节奏是计划的属性**：每天 / 隔天 / 吃 N 停 M；再配时段  |
| **停药** | 我什么时候不该吃？ | 一段**有起止**的暂停。有「临时」与「成套方案组」两种用法 |

> **关键划分（继承 v11.3 §8.1，这是全篇最重要的一条）**
>
> - **节奏只表达「该吃的日子」，不表达「不吃的原因」**——隔天吃的休息日不是停药
> - **停药只表达「这段时间不吃」，不表达节奏**——停药期不得再承载周期性
> - 二者重叠时，**停药优先**
>
> 这样划分之后，「隔天吃」用一个账号的属性就能表达，**不再需要用「计划 + 周期性停药期」两个对象拼出来**——后者正是现有系统把用户自设的常规节奏渲染成「停药中」异常状态的原因。

### 4.2 主链路：5 秒闭环

```
打开应用
  ↓
今日页按时段列出清单（早上 / 中午 / 晚上 / 睡前）
  ↓
一眼看到：待吃 2 项 · 已吃 1 项 · 今天不用吃 2 项
  ↓
点「打卡」→ 行变「已服用」，无需跳转、无需滚动
  ↓
（可选）发现打错了，点「撤销」
```

**硬要求（以 PC 宽屏为基准）**：从打开到完成一次打卡，**不需要滚动、不需要跳转、不需要二次确认**。窄屏下允许滚动，但**打卡入口不得被遮挡**、不得出现横向滚动（见 §5.3）。

### 4.3 四种状态（唯一视觉规范）

某补剂在某日**只有这四种状态**，必须各有独立视觉与独立文案：

| 状态         | 触发条件                         | 文案                              | 主按钮 | 次要入口 |
| ------------ | -------------------------------- | --------------------------------- | ------ | -------- |
| **待服用**   | 该吃 且 尚无记录                 | `待服用 1 粒`                     | 打卡   | —        |
| **已服用**   | 该吃 且 已有记录                 | `已服用 1 粒 · 早上`              | 撤销   | 追加一次 |
| **今天休息** | 节奏排到的不吃日，且未落在停药期 | `今天不用吃 · 下次 9/22`          | 无     | 仍要服用 |
| **停用中**   | 落在停药期内（无论节奏）         | `停用中 · 抗生素期间 · 9/30 恢复` | 无     | 仍要服用 |

**硬规则**：

| #   | 规则                                                                                                                          |
| --- | ----------------------------------------------------------------------------------------------------------------------------- |
| P1  | **「休息」与「停用」必须是两个不同的词**。禁止再用「停药中」表示节奏休息日                                                    |
| P2  | **每条「不吃」的项都必须给出下一个该吃的日期**。这是「怕记混」的核心解药                                                      |
| P3  | 休息日 / 停用日**不产生漏服提醒**                                                                                             |
| P4  | 休息日 / 停用日**不计入完成度分母**                                                                                           |
| P5  | 休息日 / 停用期**仍允许记录服用**（「仍要服用」）；**不弹二次确认**——本产品是记录工具，不为用户的决定设障，但记录行须标注来源 |
| P6  | 计划被整体关闭（`isActive=false`）与节奏休息是两件事，文案不得混用                                                            |

### 4.4 节奏规则

**计划的节奏字段**：

| 字段             | 类型                  | 说明                        |
| ---------------- | --------------------- | --------------------------- |
| `rateMode`       | `'daily' \| 'cyclic'` | 默认 `daily`                |
| `rateOnDays`     | `int \| null`         | cyclic 时必填，≥1（吃几天） |
| `rateOffDays`    | `int \| null`         | cyclic 时必填，≥1（停几天） |
| `rateAnchorDate` | `date \| null`        | cyclic 时必填，节奏起点     |

**判定规则**（纯函数，与停药判定分开命名、分开实现）：

```
daily    → 该吃

cyclic:
  diff = date − rateAnchorDate（按日历日）
  diff < 0                                        → 不出现（节奏尚未开始）
  diff % (on + off) < on                          → 该吃
  否则                                             → 休息日
```

**UI 预设（把用户语言直译成参数，两个入口都要给）**：

| 用户选择           | rateMode | on  | off |
| ------------------ | -------- | --- | --- |
| 每天               | `daily`  | —   | —   |
| **隔天**           | `cyclic` | 1   | 1   |
| 每 N 天一次（N≥2） | `cyclic` | 1   | N−1 |
| 吃 N 停 M          | `cyclic` | N   | M   |

> 「隔天」与「每 2 天一次」参数完全相同但用户语言不同，用户不一定会自己换算，所以两个入口都要给。

**失败方向统一为「不隐藏」**（继承 v11.3 DQ-11 决议）：
节奏或停药参数缺失 / 非法时，一律判为「该吃 / 不构成停用」，把补剂留在首页让用户看见，同时在管理页标注「配置异常，请修正」。

> 理由：数据的静默隐藏，用户没有任何发现渠道；而错误显示只是「多一行」，用户一眼即可判断。

### 4.5 停药期规则

| 场景           | 规则                                                       |
| -------------- | ---------------------------------------------------------- |
| 判定           | `startDate ≤ 该日 ≤ (endDate ?? +∞)` 即停用                |
| 范围           | 指定某一补剂，或 `'ALL'`（全部补剂一起停）                 |
| 与节奏重叠     | **停用优先**                                               |
| 与临时停药并用 | **并集**：任一覆盖该日即停用                               |
| 修改停药参数   | **只影响未来判定，已产生的记录不变**（UI 提示）            |
| 引用被删的补剂 | 条目保留并标「已删除补剂」，判定时忽略；恢复后自动重新生效 |

**两种用法**：

- **临时停药**：单条，随手加（如「这两天先不吃鱼油」）
- **方案组**：成套情景（如「抗生素期间」= 停维生素 D + 停钙片），可预设、可一键执行/停止

**方案组执行语义**：

| 场景       | 规则                                                                               |
| ---------- | ---------------------------------------------------------------------------------- |
| 执行一组   | 记 `activatedAt`；**同一时刻至多一组执行中**，执行新组自动结束旧组                 |
| 停止一组   | 记 `endedAt`，条目立即失效，**历史记录不变**                                       |
| 条目有起止 | 按条目自带起止判定                                                                 |
| 条目无起止 | 跟随组的起止（随组生、随组灭）                                                     |
| 首页表现   | 顶部显示提醒条「当前停药方案：抗生素期间（3 项）· 停止」——解决「忘了自己设过停药」 |

**明确不做**：方案组定时自动执行（与纯前端定位冲突）、多组叠加执行（保持一次一组，语义可解释）。

### 4.6 打卡与撤销

| 项   | 规则                                                                                                            |
| ---- | --------------------------------------------------------------------------------------------------------------- |
| 打卡 | 一次点击写入一条记录（日期 + 补剂 + 时段 + 数量）                                                               |
| 幂等 | 同一补剂 + 同一时段 + 同一天重复点击 → 提示「今天已打卡」，并提供**「追加一次」**（用户一天吃了两次要能记两次） |
| 撤销 | 删除该条记录，余量直接加回。**不弹二次确认**（撤销是高频安全动作）                                              |
| 加服 | 「追加一次」与「仍要服用」都写入一条独立记录                                                                    |
| 补录 | 记录归属日期由用户选，与写入时刻分开存（用于标注「补录」）                                                      |

### 4.7 回看（M2）

| 项                  | 规则                                                            |
| ------------------- | --------------------------------------------------------------- |
| 日历                | 一屏一个月，**四态视觉可区分**（吃了 / 休息 / 漏服 / 停用）     |
| 点某日              | 显示当日全部记录 + 四态文案                                     |
| 休息日 / 停用日详情 | 文案分别为「今日休息」「停用中 · X 日恢复」，**不提供补录入口** |
| 漏服发现            | 超过补录窗口的漏服，在日历上加标记（低成本方案，不动提醒范围）  |
| 补录窗口            | 默认过去 7 天，不含今天。**今日漏服次日补**，与次日提醒口径一致 |

### 6.9 每日成分汇总口径（M3）

四条必须写死的规则：

| #   | 规则                                                                                                                   |
| --- | ---------------------------------------------------------------------------------------------------------------------- |
| 1   | **只统计 `taken = true` 的记录**。漏服标记、计划外加服按各自的 `taken` 判定                                            |
| 2   | **按 `date` 匹配当时有效的配方**（用 `effectiveFrom` / `effectiveTo`），**不按录入时刻**                               |
| 3   | **单位归一化**：mg / μg / g 归一到 μg 后累加；**IU 与 ml 独立累加，不与 μg 混算**；显示时按合计值选单位                |
| 4   | **只做累加与并列，不做判断**。可以显示「参考值 800 / 今日 1200」，**不得出现「过量」「有害」「建议减少」等结论性措辞** |

> **第 4 条是本模块的合规边界。** 产品定性是记录工具，阈值全部由用户自填，系统只做加法与并列展示，不解释含义。

**删除补剂时的处理**：删除补剂的二次确认中询问「同时删除该补剂的 N 条历史记录」（默认勾选）。勾选则记录一并删除，成分汇总不会留下无法解析来源的孤儿数据。
