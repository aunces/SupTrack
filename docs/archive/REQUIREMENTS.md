## 3. 增补条款（ADD）

> v10.1 未覆盖、但产品必须明确的规则。这些是 v11.0 的**新增内容**。

### ADD-01 首页"今日记录"区块的定位 `【超出→补正式条款】`

v10.1 4.1 定义首页为"计划清单 + 成分汇总 + 预警"，未含记录列表，但 3.1 要求"支持对历史记录进行修改、补充、删除"。实现用"今日记录"卡片补上了这个入口。

**建议正式定义为**：

- 首页存在两个数据视图，职责必须区分：
  - **时段清单**（主）：回答"**还剩什么没做**"，只含当日应服计划项
  - **今日记录**（辅）：回答"**今天实际发生了什么**"，含全部来源（计划打卡 / 手动录入 / 补录）
- 二者必然重叠（已打卡项同时出现），这是**设计取舍而非缺陷**，但必须避免让用户以为有两份数据
- **待决策**：是否合并为单一视图（见 DQ-03）

### ADD-02 补录计划外服用（extra）的入口 `【盲区】`

v10.1 5.8 定义了"补录无计划 → `status=extra`"的**数据规则**，但未定义**入口**：补录弹窗只列计划项，无计划项根本不出现。

**待补齐的规则**：

- 补录弹窗底部需提供"添加计划外补剂"入口，可选任意补剂 + 时段 + 数量
- 提交后：`planId=null`、`plannedAmountSnapshot=null`、`plannedAmountSource=unavailable`、`status=extra`
- 该入口同样受补录窗口限制，且不参与完成度分子分母

### ADD-03 完成度口径的精确表述 `【澄清】`

v10.1 有两处表述，需合并为一条无歧义规则：

- 3.7：「已服计划项 ÷ (应服计划项 − 停药期排除项)」「**手动录入不计入完成度**」
- 5.8：「补录记录计入对应 `date` 的完成度」「补录"漏服"计入分母不计入分子」

冲突点：补录记录 `source=manual`，按 3.7 应"不计入"，按 5.8 应"计入"。实现采用的判定口径同时满足两者意图：

```
分子 = 命中「应服计划项」（补剂 + 时段匹配）且满足以下任一：
        · source = plan（当日打卡）
        · plannedAmountSource = current_plan（补录命中计划）
      且 status ∈ { taken, partial }

分母 = 该日启用计划按 timeSlots 展开去重（停药日项直接排除）
       分母为 0 → 完成度 = null（UI 显示"无计划"）

不计入分子：今日手动录入（unavailable）、补录无计划（extra）、skipped、已软删除记录
```

**v11.0 采信实现口径**——它是唯一能同时满足 v10.1 3.7 与 5.8 两条要求的判定方式。建议以此段落替换 v10.1 3.7 的原表述。

### ADD-04 计划唯一性约束 `【盲区】`

v10.1 未约束"同一补剂在同一时段是否允许多条启用计划"。当前若存在两条，首页会出现两个打卡项，各自独立扣库存——**同一时段吃双倍且用户不自知**。

**待补齐的规则**：

- 同一 `supplementId` 的启用计划，`timeSlots` 之间**不得重叠**（创建/编辑计划时校验并提示）
- 若用户确实需要一天两次，正确做法是调整 `dailyAmount` 并拆时段，而非建两条计划

### ADD-05 第 8–30 天漏服的发现路径 `【盲区】`

v10.1 固定次日提醒范围为 7 天（P2 才考虑可配置），补录窗口为 30 天。结果是**第 8–30 天的漏服有补录能力、无发现路径**。

**待补齐的规则**（二选一，见 DQ-06）：

- A：日历上为"有漏服且仍在补录窗口内"的日期加标记
- B：提醒范围跟随补录窗口（需评估性能）

### ADD-06 数据安全的底线声明 `【澄清】`

v10.1 第 13 节已决策"自动本地快照 — 不做"，第 11 节要求"用户需自行定期导出备份"，但**没有任何机制提醒用户去备份**——这是纯本地应用最大的单点风险。

**v11.0 建议**（见 DQ-05）：保留"不做自动快照"的决策，但补一条**备份提醒**：距 `Meta.lastExportAt` 超过 N 天且期间有新增记录时，首页提示一次（可关闭）。

### ADD-07 术语可读性 `【新增】`

`IU` / `μg` / `mcg` 在非专业场景下容易混淆。

**待补齐**：首次出现时提供术语解释（如"IU = 国际单位，用于维生素 A/D/E，不参与 mg/μg 换算"）。不改数据模型，仅文案。

## 8. 主链增补（v11.1 ~ v11.2）：节奏模型、首页信息结构与停药方案组

> **本节是 v11.1 的核心新增内容。** 起因：用户最初的原始需求只有两件事——「某个补剂隔天吃，怕记混」+「停药期」，而当前系统需要用「计划（每天吃）+ 停药期（周期性 吃 1 停 1）」两个对象才能拼出"隔天吃"，且休息日会在首页被渲染成"停药中"——**用户自己设的常规节奏，被系统当成异常状态展示**。
>
> **本轮已确认的三个前提**（用户 2026-09-20）：节奏归计划 · 范围全留只做对主链 · 本轮只出条款不改代码。

### 8.1 概念划分（术语补充，优先于 v10.1 中"停药期"的相关用法）

| 概念             | 含义                 | 归属           | 时间性质             | 回答的问题       |
| ---------------- | -------------------- | -------------- | -------------------- | ---------------- |
| **节奏 Rate**    | 长期规律：多久吃一次 | **计划的属性** | 无限期，直到计划失效 | "我该哪天吃"     |
| **停药期 Pause** | 一段有起止的暂停     | **独立实体**   | 有限期，有明确起止   | "我这段时间不吃" |

三条划分规则：

1. **节奏只表达"该吃的日子"，不表达"不吃的原因"**——隔天吃的休息日不是停药
2. **停药期只表达"这段时间不吃"，不表达节奏**——停药期不得再承载周期性
3. **二者重叠时，停药期优先**——即使某日按节奏"该吃"，只要落在停药期内就判为"停用"

> **补充概念：停药方案组**（详见 §8.13）——"一束可切换的停药配置"，用于成套情景（生病用药、出差、体检前停某些补剂）。它是停药期的**组织层**，不引入新的判定类型。
>
> 这样划分后，"停药"两个字恢复只表示真正的停药。已有 DQ-10（"停药期"命名偏医疗）随之自然解决：节奏部分不再借用"停药"一词。

### 8.2 数据模型变更

**`DosagePlan` 新增 4 个字段**（v10.1 2.4 的扩展）：

| 字段             | 类型                  | 必填条件             | 说明                              |
| ---------------- | --------------------- | -------------------- | --------------------------------- |
| `rateMode`       | `'daily' \| 'cyclic'` | 必填，默认 `'daily'` | 节奏模式                          |
| `rateOnDays`     | `number \| null`      | `cyclic` 时必填，≥1  | 吃几天                            |
| `rateOffDays`    | `number \| null`      | `cyclic` 时必填，≥1  | 停几天                            |
| `rateAnchorDate` | `string \| null`      | `cyclic` 时必填      | 节奏起点（本地日期 `YYYY-MM-DD`） |

**Zod 约束**（沿用 `pausePeriod.ts` 中 C-5"部分更新不误报"的写法）：

- `rateMode='daily'` → 其余三字段必须为 `null`
- `rateMode='cyclic'` → 三字段必须非空，且 `rateOnDays ≥ 1`、`rateOffDays ≥ 1`
- 提示文案统一为：`周期节奏必须填写起始日期与吃/停天数；非周期节奏不得填写周期参数`

**`PausePeriod` 收窄**（本轮决议 DQ-12：**直接删除，不留 deprecated 占位**）：

- `cycleMode` / `cycleStartDate` / `cycleOnDays` / `cycleOffDays` 四个字段**从 schema 与 Zod 校验链中移除**
- `supplementId=null`（旧的"全局停药"）不再新增，改由 **§8.13 方案组的 `'ALL'` 条目**承担
- 判定简化为：`该日期 ∈ [startDate, endDate ?? +∞]` 即为停用
- **并集语义保留**，但来源变为：临时停药条目 ∪ 当前执行中方案组的条目

### 8.3 节奏判定规则

新增纯函数 `isScheduledOnDate(plan, date)`（**必须与 `isPausedOnDate` 分开命名，禁止复用**——两者判定方向相反）：

```
rateMode = 'daily'   →  true（该吃）

rateMode = 'cyclic':
  diff = differenceInCalendarDays(parseISO(date), parseISO(rateAnchorDate))
  diff < 0                       →  false（节奏尚未开始）
  diff % (rateOnDays + rateOffDays) < rateOnDays  →  true（落在"吃"的区间）
  否则                            →  false（休息日）
```

**硬规则（5 条）**：

| #   | 规则                                                        | 理由                                                                                                                                                                                                                                                                             |
| --- | ----------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| R1  | **锚点当天 = 周期第 1 天（吃）**                            | 与停药期原逻辑（`pause.ts:21`）保持同向，避免迁移后节奏整体错位一天                                                                                                                                                                                                              |
| R2  | 休息日判定写作 `diff % (on+off) >= on`，该吃判定写作 `< on` | 两条规则方向相反，必须分别实现并各自有单测                                                                                                                                                                                                                                       |
| R3  | **节奏参数缺失或非法时，判为"该吃"而非"不吃"**              | 与现有 `isPaused` 的失败方向相反，故需统一。按"不吃"处理会让补剂静默消失、用户无从发现；按"该吃"处理会出现在首页，用户自己判断。**已定（DQ-11）：`isPausedOnDate` 的参数缺失/非法同样判为"不停用"（`return false`），两处失败方向统一为"不隐藏"**，并在补剂库/停药页标注配置异常 |
| R4  | `diff < 0`（锚点在未来）→ 该日不出现该补剂                  | 节奏尚未开始，不应产生应服项                                                                                                                                                                                                                                                     |
| R5  | 同一补剂多个 `timeSlots` 各自独立判定                       | 一天两次的场景由 `dailyAmount` + 多时段表达，不靠节奏                                                                                                                                                                                                                            |

**UI 预设（把用户语言直译成参数）**：

| 用户选择           | rateMode | rateOnDays | rateOffDays |
| ------------------ | -------- | ---------- | ----------- |
| 每天               | `daily`  | —          | —           |
| **隔天**           | `cyclic` | 1          | 1           |
| 每 N 天一次（N≥2） | `cyclic` | 1          | N−1         |
| 吃 N 停 M          | `cyclic` | N          | M           |

> "隔天"与"每 2 天一次"参数完全相同但用户语言不同，两个入口都要给（用户不一定会自己换算）。

### 8.4 计划唯一性约束（采纳 ADD-04 / DQ-01）

与节奏同属"计划的语义约束"，一并定掉：

- 同一 `supplementId` 的启用计划，`timeSlots` 之间**不得重叠**
- 创建/编辑计划时校验并阻止，提示：`该补剂在「早」已有计划，请合并为一条或调整时段`
- 需要一天两次时，正确做法是调整 `dailyAmount` 并拆时段，而不是建两条计划
- 存量数据若已存在重叠，导入/启动时列出清单提示用户处理，不自动合并

### 8.5 四态呈现规则（MOS-1 + MOS-2）

某补剂在某日**只有四种状态**，必须各有独立视觉与独立文案：

| 状态         | 触发条件                   | 首页文案                 | 主按钮 | 次要入口              |
| ------------ | -------------------------- | ------------------------ | ------ | --------------------- |
| **待服用**   | 该吃 且 该时段无记录       | `待服用 N 粒`            | 打卡   | —                     |
| **已服用**   | 该吃 且 已有记录           | `已服用 N 粒 · 早`       | 撤销   | 追加一次（见 DEV-01） |
| **今日休息** | 节奏休息日 且 未落在停药期 | `今天不用吃 · 下次 9/22` | 无     | 仍要服用（见 DQ-13）  |
| **停用中**   | 落在停药期内（无论节奏）   | `停用中 · 9/30 恢复`     | 无     | 仍要服用              |

**硬规则（6 条）**：

| #   | 规则                                                                                                                                                                                |
| --- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| P1  | **「休息」与「停用」必须是两个不同的词**。禁止再用"停药中"表示节奏休息日                                                                                                            |
| P2  | **每条"不吃"的项都必须给出下一个该吃的日期**（`nextScheduledDate`，由 R1 规则向前推算，迭代上限 366 次，超限显示"未确定"）                                                          |
| P3  | 休息日 / 停用日**不产生漏服提醒**（`detectMissedPlans` 已正确排除停药日，需同步扩展到节奏休息日）                                                                                   |
| P4  | 休息日 / 停用日**不计入完成度分母**（沿用 `computeDayStat` 现有排除逻辑，扩展判定条件）                                                                                             |
| P5  | 停用期 / 休息日仍允许服用（「仍要服用」），写入 `source=manual`、`status=extra`；**不弹二次确认**（本产品是记录工具，不为用户的决定设障），但记录行须标注来源。写入语义详见 §8.13.4 |
| P6  | 计划 `isActive=false` 与节奏休息是两件事：前者是计划整体关闭，后者是本次循环的休息日。文案不得混用                                                                                  |

### 8.6 首页信息结构（MOS-3）

**唯一主结构 = 今日清单**，按时段分组（早 / 中 / 晚 / 睡前），每个补剂一行。

**分区与顺序**：

1. **待服用区**——含"待服用"与"已服用"两类行，按时段分组
2. **「今天不用吃」折叠行**——默认收起为一行汇总（`今天不用吃（2 项）`），展开显示各补剂 + 原因（休息 / 停用）+ 下次日期
3. **提醒条**——漏服补录提示（`MissedPlansBanner`）+ 库存预警（负库存 / 临期 / 不足 7 天），保持现状
4. **「其他记录（N）」卡片**——**只列不在清单里的记录**：计划外服用、手动录入、补录到的历史项；无内容时整卡不渲染
5. **今日成分摄入**——保持现状

**硬规则（4 条）**：

| #   | 规则                                                                                                                          |
| --- | ----------------------------------------------------------------------------------------------------------------------------- |
| H1  | **同一批数据只允许出现一次**：已打卡的计划项只出现在清单里（呈"已服用"态），不再进入记录列表 → 关闭 ADD-01 的模糊地带与 DQ-03 |
| H2  | 当天只有休息/停用项、无待服用项时，不显示"今天没有启用的计划"，而显示 `今天不用吃 · 下次 9/22`                                |
| H3  | 待服用项数 = 0 且全部已服用时，清单区给出完成反馈（如 `今天的 3 项都完成了`）                                                 |
| H4  | 折叠行展开状态按会话记忆，不持久化（避免用户抱怨"我的东西不见了"）                                                            |

### 8.13 停药方案组（新增能力，来自用户 2026-09-20 提案）

> **提案原话**：「出个方案组，比如 A 组对多种补剂设计不同停药期，B 组全局停药，可以选择执行哪一组」

#### 8.13.1 要解决的问题

现有"停药期"是**一条一条记**的：生病要停 3 个补剂，就得建 3 条记录，事后还要逐条删。换季、生病用药、出差、体检前停某些补剂这类**成套情景**，需要"预设 + 一键切换"。

#### 8.13.2 概念模型

| 实体                           | 字段                                                                                                                        | 说明               |
| ------------------------------ | --------------------------------------------------------------------------------------------------------------------------- | ------------------ |
| **停药方案组 `PauseScheme`**   | `id` / `name`（如"抗生素期间"）/ `note` / `isActive` / `activatedAt` / `endedAt?` / `deletedAt` / `createdAt` / `updatedAt` | 一个具名的停药情景 |
| **方案条目 `PauseSchemeItem`** | `id` / `schemeId` / `supplementId \| 'ALL'` / `startDate?` / `endDate?` / `reason?` / `deletedAt`                           | 组内一条停用规则   |

三个要点：

1. 条目的补剂范围支持 **`'ALL'`（全部补剂）**——这就是用户说的"B 组全局停药"，同时替代了被删除的旧"全局停药期"
2. 组内不同条目可以有**各自不同的起止日期**——这就是"A 组对多种补剂设计不同停药期"
3. 条目起止可留空，留空时**跟随组的执行区间**（见 8.13.3）

#### 8.13.3 执行语义

| 场景                 | 规则                                                                                                                    |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| 执行一组             | 记 `isActive=true`、`activatedAt=执行当日`；**同一时刻至多一组处于执行中**，执行新组即自动结束旧组（记 `endedAt=当日`） |
| 停止一组             | 记 `isActive=false`、`endedAt=停止当日`                                                                                 |
| 条目有起止           | 按条目自带的起止判定                                                                                                    |
| 条目无起止           | 按组的 `[activatedAt, endedAt ?? +∞]` 判定（随组生、随组灭）                                                            |
| 与"临时停药"的关系   | **并集**：临时停药条目 ∪ 当前执行中方案组的条目，任一覆盖该日即判"停用"（沿用 v10.1 5.3 并集语义）                      |
| 切换组时已有记录     | **不回滚、不修改**——只改变未来判定（与现有"修改周期参数只影响未来计算"口径一致）                                        |
| 被引用的补剂被软删除 | 条目保留并标"已删除补剂"，判定时忽略；补剂恢复后条目自动重新生效                                                        |

**明确不做的事**（避免范围蔓延）：

- 不做方案组的定时自动执行（如"每月 1 号自动执行"）——需要后台能力，与纯前端定位冲突
- 不做方案执行历史的时间轴回溯统计——P2 再议
- 不做多组叠加执行——保持"一次一组"，语义可解释

#### 8.13.4 「仍要服用」的写入语义（落实 DQ-13）

在「今日休息」「停用中」两类行上提供次要按钮「仍要服用」。

| 项                   | 规则                                                                                                                                                                             |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 写入                 | `DailyIntake`：`source=manual`、`status=extra`、`planId=当前时段匹配计划?.id ?? null`、`plannedAmountSnapshot=null`、`plannedAmountSource=unavailable`                           |
| 库存                 | 照常扣减（`StockLog.reason=manual_intake`）                                                                                                                                      |
| 完成度               | 不计入分子、不计入分母（与 `extra` 现有口径一致）                                                                                                                                |
| 二次确认             | **不弹确认**。本产品是记录工具，不为用户的决定设障；但记录行必须标注来源（`休息日服用` / `停药期服用`）                                                                          |
| 频次                 | 同一日同一时段可重复触发（一天加服两次要能记两次）                                                                                                                               |
| 与「手动录入」的边界 | 「仍要服用」只加在**清单内已存在的行**上（该补剂当天正在被记录）。**补剂当天完全没出现在清单里**（计划未启用 / 节奏未开始 / 无计划）时，走现有「手动录入」入口，不新增第三个入口 |

#### 8.13.5 界面落点

| 位置              | 内容                                                                                                           |
| ----------------- | -------------------------------------------------------------------------------------------------------------- |
| 停药页            | 升级为「停药」页，两个分区：**方案组**（列表 + 一键执行/停止 + 当前执行中高亮）/ **临时停药**（现有单条 CRUD） |
| 首页 · 停用中行   | 文案标明来源：`停用中 · 抗生素期间 · 9/30 恢复`（来自方案组时显示组名）                                        |
| 首页 · 顶部提醒条 | 有方案组执行中时显示一行 `当前停药方案：抗生素期间（3 项） · 停止`——解决"我忘了自己设过全局停药"的问题         |
| 日历 · 日期详情   | 停用日标明来自哪个方案组                                                                                       |

#### 8.13.7 DQ-14 补充解释：首页"其他记录"卡片到底是什么

**它现在是什么**：首页底部那张 `今日记录（N）` 卡片，列出当日**全部**记录（计划打卡 + 手动录入 + 补录），每行带"修改"与"撤销"。

**它为什么存在**：它是**历史修正入口**。时段清单只能"打卡/撤销"，改数量得走这张卡——没有它，"今天吃错了想改"就没有入口。

**它的问题**：与清单重叠。已打卡的补剂会同时出现在清单（行内显示"已服用"）和这张卡里，同一件事看两遍；而手动录入的补剂又只出现在卡片里、不进清单，看起来像两份数据。

**决议（保留但收窄）**：卡片改名为 **「计划外与其他记录（N）」**，只装**清单里没有的记录**——计划外服用（`extra`）、手动录入、「仍要服用」。已打卡的计划项只在清单里出现一次。

**为什么保留而不删**：

| 若删掉           | 后果                                                                      |
| ---------------- | ------------------------------------------------------------------------- |
| 修改入口没了     | 打卡数量填错只能"撤销 + 重新打卡"，多一次库存回滚，还会多留一条回收站记录 |
| 计划外服用看不见 | `extra` 记录将没有任何展示位置，等于"记了但看不到"                        |
| 补录结果无法核对 | 补录完成后用户无处确认到底写进去了什么                                    |

所以它保留，但**收窄职责**：清单负责"该做什么"，这张卡只负责"清单之外还发生了什么"。
