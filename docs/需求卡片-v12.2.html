01

原始需求：只有两件事

一切复杂度的合法性来源

「某个补剂隔一天吃，怕记混」

本质问题：今天到底该不该吃？

验收标准：打开就看到「今天吃 / 今天不吃，下次 X 日」

「还有停药期」

本质问题：有一段时间不吃，这段时间别提醒我。

验收标准：停用期间该补剂整体静音，且说清什么时候恢复

「怕记混」其实包含三个问题——它决定了功能边界

  • Q1 今天该吃什么？→ 今日清单（四态）· 每天 1–3 次
  • Q2 我吃了吗？→ 打卡 · 每天 3–7 次
  • Q3 昨天吃了吗？→ 回看 / 日历 · 偶尔（怀疑记错时）

Q1 + Q2 是每天发生的高频动作，Q3 是低频补位。现有系统的绝大部分复杂度，都花在既不回答 Q1、也不回答 Q2 / Q3 的地方。

02

跑偏诊断

把「记录工具」当成「库存系统」做了

约 45% 规范篇幅

服务于「库存与撤销的正确性」这一个问题，而它不回答用户的任何一个疑问。

根源是一个技术选择

用软删除实现「撤销」。为回答「恢复一条被撤销的记录时，要不要再扣一次库存」，长出了整套机制。

一次性归零

把撤销改成「直接删记录 + 余量加回」，以下全部消失：

  • 4 态 stockState 状态机
  • StockLog 库存流水表
  • purge 语义
  • unknown 二选一对话框
  • 双扣警告

合计约 300 行规范

03

五项决策 · 全部收口

2026-09-20 定案，本卡片即开发基线
D1

余量要不要自动扣？

单一数字，自动加减 方案 B

补剂上一个整数余量，可留空。打卡减、撤销加。不做流水、不做状态机、不做批次——保留「还能吃几天」的价值，同时让状态机规范整块归零。

D2

回收站与软删除要不要留？

砍掉，硬删除 + 确认 方案 A

复杂度大头。改硬删除 + 二次确认，删除框内提示「建议先导出备份」；误删靠导出兜底。

D3

成分库与每日汇总做不做？

完整保留，放 M3 定案

两表 M3 追加，直接搬现有实现（与库存状态机无耦合），仅把汇总口径改为「只统计已服用记录」。不进 M1。

D4

重构策略选哪条？

换心脏、留脚手架 方案 A

数据模型与主链页面重写；Dexie / Zod / 导出导入 / PWA / 组件库 / 测试脚手架直接搬。无存量数据 → 重写零迁移成本。

D5

目标平台以哪个为主？

PC 优先 用户指定

未采纳原「手机优先」建议。移动适配后期再说；窄屏可用从「必须优先满足」下调为「不破坏」（不横向滚动、不遮挡入口），移动端专门适配列入明确不做。

04

整个产品只有三个概念

补剂 · 计划 · 停药

补剂

回答：我有哪些？

一个名字 + 每次吃多少 + 单位；余量可选。

计划

回答：我该什么时候吃？

节奏是计划的属性：每天 / 隔天 / 每 N 天一次 / 吃 N 停 M；再配服用时段。

停药

回答：我什么时候不该吃？

一段有起止的暂停。两种用法：临时停药（单条）、方案组（成套情景，一键执行/停止）。

全篇最重要的一条划分

  • 节奏只表达「该吃的日子」，不表达「不吃的原因」——隔天吃的休息日不是停药
  • 停药只表达「这段时间不吃」，不表达节奏——停药期不得再承载周期性
  • 二者重叠时，停药优先

这样划分之后，「隔天吃」用计划的一个属性就能表达，不再需要用「计划 + 周期性停药期」两个对象拼出来——后者正是现有系统把用户自设的常规节奏渲染成「停药中」异常状态的原因。

05

四种状态

某补剂在某日只有这四种，必须各有独立视觉与独立文案
待服用
该吃 且 尚无记录
待服用 1 粒
主按钮：打卡
已服用
该吃 且 已有记录
已服用 1 粒 · 早上
主按钮：撤销　次要：追加一次
今天休息
节奏排到的不吃日，且未落在停药期
今天不用吃 · 下次 9/22
无主按钮　次要：仍要服用
停用中
落在停药期内（无论节奏）
停用中 · 抗生素期间 · 9/30 恢复
无主按钮　次要：仍要服用

六条硬规则

  • P1 「休息」与「停用」必须是两个不同的词。禁止再用「停药中」表示节奏休息日
  • P2 每条「不吃」的项都必须给出下一个该吃的日期——这是「怕记混」的核心解药
  • P3 休息日 / 停用日不产生漏服提醒
  • P4 休息日 / 停用日不计入完成度分母
  • P5 休息日 / 停用期仍允许记录服用，不弹二次确认——本产品是记录工具，不为用户的决定设障，但记录行须标注来源
  • P6 计划被整体关闭（isActive=false）与节奏休息是两件事，文案不得混用
打开应用→ 今日页按时段列出清单→ 一眼看到：待吃 2 · 已吃 1 · 今天不用吃 2→ 点「打卡」→ 行变「已服用」

硬要求（以 PC 宽屏为基准）：从打开到完成一次打卡，不需要滚动、不需要跳转、不需要二次确认。窄屏下允许滚动，但打卡入口不得被遮挡。

06

需求分层

L0 核心 / L1 支撑 / L2 增值 / L3 明确不做

L0 · 核心 M1 交付

7 项 · 缺一不可

  • C-01 记录补剂（名称、每次吃几个、单位）
  • C-02 给补剂设计划：每天 / 隔天 / 每 N 天一次 / 吃 N 停 M
  • C-03 计划含服用时段（早 / 中 / 晚 / 睡前）
  • C-04 今日页：按时段列出「今天该吃什么」，四态清晰
  • C-05 打卡（一次点击）与撤销
  • C-06 停药期：一段有起止的暂停，期间该补剂静音
  • C-07 数据存本地、可离线打开

L1 · 支撑 M1 内完成

4 项 · 必须有，但要做到极简

  • S-01 余量记录 —— 单一数字，打卡减、撤销加
  • S-02 删除 —— 硬删除 + 二次确认
  • S-03 一键导出 JSON 兜底 —— 误删不可恢复，靠手动备份
  • S-04 PC 优先，窄屏不破坏 —— 侧边导航 + 键盘可操作；窄屏仅要求不横向滚动、不遮挡入口

L2 · 增值 M2 / M3

7 项 · 按需再做

  • V-01 日历回看（一屏一个月，四态可辨）· M2
  • V-02 补录：昨天忘了打，今天补一下（窗口 7 天）· M2
  • V-03 停药方案组：成套情景预设 + 一键切换 · M2
  • V-04 「仍要服用」：休息日 / 停用期也能记一笔 · M2
  • V-05 过期提醒、余量不足提醒 · M3
  • V-06 成分库与每日成分汇总 · M3 已定案
  • V-07 备份提醒、统计图表 · M3

L3 · 明确不做 越界即范围蔓延

本轮及可预见范围内

  • 软删除与回收站（D2 已砍）
  • 库存 4 态状态机 + 库存流水 StockLog
  • unknown 记录二选一对话框、双扣警告
  • 记录状态四枚举 → 降为「吃了 / 没吃」+ 额外标记
  • 计划量快照三态、历史真实性过滤
  • 8 跳 Schema 迁移链（无存量数据）
  • 移动端专门适配（触摸手势、底部导航、44px 热区、安全区）
  • 身体反馈、库存批次、快速录入组合
  • 成分冲突 / 超标提醒（接近医学判断）
  • 统计报表（现有代码连路由入口都没有）
07

数据模型

能用一个数字表达的，不建一张表；能用布尔表达的，不建枚举
表 名称 关键字段与要点 里程碑
1 Supplement
补剂 		name · unitType · stockCount（余量，可选，单一数字） · stockUnit / unitsPerStock（仅 UI 换算）· expiryDate · notes 本轮
2 DosagePlan
计划（含节奏） 		supplementId · amountPerTime · timeSlots[] · rateMode（daily/cyclic）· rateOnDays / rateOffDays / rateAnchorDate · isActive
约束：同一补剂的启用计划，时段不得重叠 		本轮
3 DailyIntake
记录 		date（服用归属日，补录时为所选历史日）· supplementId · planId? · timeSlot · amount · taken（布尔） · isExtra · createdAt（真实写入时间，与 date 不同则标「补录」） 本轮
4 PausePeriod
停药 		schemeId? · supplementId 或 'ALL' · startDate? · endDate?（空 = 持续中）· reason 本轮
5 PauseScheme
停药方案组 		name（如「抗生素期间」）· isActive · activatedAt / endedAt
同一时刻至多一组执行中 		本轮
6 Meta
元数据 		key / value —— schemaVersion · lastExportAt · appVersion 本轮
7 Ingredient
成分 		name（跨补剂归并的唯一锚点）· unit（mg/μg/g/IU/ml，存储统一 μg）· recommendedDailyIntake? · upperLimit?（用户自填，系统不预置） M3
8 SupplementIngredient
补剂-成分关联 		supplementId · ingredientId · amountPerServing · effectiveFrom / effectiveTo（配方版本管理：改配方不修改原记录，旧记录失效日＝昨日，新建今日生效） M3

每日成分汇总口径（M3）—— 四条必须写死的规则

  • 1 只统计 taken = true 的记录
  • 2 按 date 匹配当时有效的配方，不按录入时刻（回看昨天，用的是昨天的含量）
  • 3 mg / μg / g 归一到 μg 后累加；IU 与 ml 独立累加，不与 μg 混算
  • 4 只做累加与并列，不做判断——可以显示「参考值 800 / 今日 1200」，不得出现「过量」「有害」「建议减少」

第 4 条是本模块的合规边界。产品定性是记录工具、阈值全部由用户自填，系统只做加法与并列展示，不解释含义。

08

开发路径：换心脏，留脚手架

三个里程碑，M1 做完即可替换现有应用

M1 · 核心闭环 先做

今日页四态清单 + 打卡 + 撤销；补剂页含节奏配置；单条临时停药；本地存储 + 离线。

完成定义：建 3 个补剂（其中一个隔天吃）→ 首页正确显示今天吃什么 → 打勾 → 第二天打开答案仍然正确

M2 · 回看与补录

日历四态可辨；补录（窗口 7 天）；停药方案组；「仍要服用」。

完成定义：翻回上周，能一眼看出哪天漏了、哪天在停药

M3 · 增值

成分库与每日成分汇总（已定案）、余量提醒、备份提醒、统计。

完成定义：随便挑一个砍掉，不影响 M1 / M2 使用

「搬」而不是「重写」的部分

Dexie 封装与事务写法 · Zod 校验模式 · 导出导入与备份 · 离线 / PWA 配置 · UI 组件库与布局外壳 · 测试脚手架（Vitest + fake-indexeddb）

重写：数据模型、四态判定、今日页、计划与节奏、停药与方案组、库存扣减逻辑。删除：整块库存状态机、8 跳迁移链。

查看明天 → 显示「今天不用吃 · 下次 X 日」，不出现「停药中」

10

边界与红线

写在最前面，用于挡住范围蔓延
不做医疗建议与健康结论
阈值全部用户自填，系统不预置默认值。成分汇总只累加与并列，不出现「过量」「建议减少」等结论性措辞。
不做静默隐藏
节奏 / 停药参数缺失或非法时，一律判为「该吃」，把补剂留在首页让用户看见，同时在管理页标注「配置异常，请修正」。
M3 项不得提前进入 M1
成分库、提醒、统计都在 M3。范围蔓延是本项目最大的需求风险。
不做移动端专门适配
D5 定为 PC 优先。窄屏只需「不破坏」；触摸手势、底部导航、44px 热区、安全区适配将来确有需要时单独立项。
误删不可恢复
D2 砍掉回收站后的已知代价。缓解：删除二次确认 + 确认框内提示「建议先导出备份」+ M3 补备份提醒。
不做云同步与后端
纯前端、本地存储、离线可用。方案组定时自动执行因与纯前端定位冲突，亦不做。
